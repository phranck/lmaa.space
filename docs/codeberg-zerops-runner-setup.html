Schritt 2

User-Level Runner-Token holen

Du
  • https://codeberg.org/user/settings/actions/runners öffnen.
  • "Create new Runner" klicken. Token erscheint nur einmal — sofort in 1Password / sicherer Notiz parken.

User-Level (nicht Repo-Level) gewählt, damit derselbe Runner später auch für musiccloud, layered.work etc. Jobs annimmt. Repo-Level-Token wäre an ci-runner selbst gebunden — wir brauchen Account-Scope.

Schritt 4

Zerops-Projekt ci-runners anlegen

Du
  • Zerops-Dashboard → + New Project.
  • Name: ci-runners · Region: beliebig (Prag = niedrigste Latenz zu Codeberg-EU).
  • Project-ID notieren — brauchst du falls du zcli push nutzt (Variante a/c unten).
Schritt 5

Ubuntu-24.04-Service anlegen

Du
  • Im Projekt ci-runners → + Add Service → Ubuntu 24.04.
  • Service-Name: runner (muss dem setup:-Eintrag in zerops.yml entsprechen).
  • Resources: 2 vCPU shared / 4 GB RAM / 10 GB Disk.
  • Persistent Volume: 1 GB anlegen, Mount Path: /data. Ohne das registriert sich der Runner bei jedem Restart neu und hinterlässt Karteileichen auf Codeberg.
  • Ports: keine (Runner connectet nur outbound zu codeberg.org).

Deploy-Variante (Zerops ↔ Codeberg)

Da Zerops Codeberg nicht als Git-Source kennt, eine der drei Varianten wählen:

Variante Wie Trade-off
a) zcli push manuell Service ohne Git-Source anlegen, lokal zcli push --project-id … --service-id runner für jeden Update. Voll unter deiner Kontrolle, keine Mirror-Pflege. Manueller Schritt bei jedem Runner-Update.
b) GitHub-Mirror Repo zusätzlich als github.com/phranck/ci-runner spiegeln, Zerops auf den GH-Mirror hängen. Auto-Build bei jedem Push. Codeberg bleibt Source-of-Truth, GH-Mirror muss synchron bleiben.
c) Erst-Setup via zcli, dann ruhen lassen Wie (a), aber Updates sind selten (forgejo-runner-Version-Bumps alle paar Monate). Einfachster Pfad. Pragmatisch wenn der Runner stabil läuft.

Empfehlung: Variante c als Default — zcli push einmalig jetzt, dann Wartung nur bei forgejo-runner-Version-Updates.
