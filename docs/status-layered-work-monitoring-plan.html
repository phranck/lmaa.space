Status Layered Work Monitoring Plan

Umsetzungsplan für eine unabhängige Status-Website unter status.layered.work. Der erste Schritt kommt bewusst ohne Zerops API aus: Projekte, Services und Endpoints werden statisch konfiguriert. Die Website unterstützt Light/Dark Mode automatisch nach Systempräferenz und manuell per Theme-Toggle. Die aktuelle Umsetzung nutzt React, Vite, Tailwind CSS und eigene Design-Tokens ohne shadcn.

Stand: 2026-05-26 Domain: status.layered.work UI: React/Vite/Tailwind, ohne shadcn Theme: system, light, dark Phase 1: ohne Zerops API X-Status-Token: Pflicht

1. Zielbild

Die Status-Website soll projektübergreifend anzeigen, ob öffentliche und interne Services funktionieren. Sie soll nicht nur HTTP-Status anzeigen, sondern auch Antwortzeiten, Prozess-Uptime, Dependency-Checks und historische Uptime-Werte darstellen.

  • Einheitliche Status-Endpunkte pro öffentlich erreichbarem Service.
  • Interne Dienste wie Datenbanken, Object Storage und GeoDB werden nicht direkt öffentlich gemacht.
  • Die Status-Website misst externe Response-Zeiten und berechnet historische Uptime selbst.
  • Services liefern ihren lokalen Zustand und Dependency-Checks über JSON.
  • Die UI verwendet eigene React-Komponenten, Tailwind CSS, CSS Design-Tokens und unterstützt Light/Dark Mode automatisch und manuell.

2. Abgrenzung für Phase 1

In Scope

  • Statische Projekt- und Service-Konfiguration.
  • Status-Endpunkte /_status/live und /_status/ready.
  • Status-Website mit eigenen React-Komponenten, Cards, Badges und Theme-Toggle.
  • Ping-Zeiten, letzter Check, Prozess-Uptime und historische Uptime.
  • Schutz der Status-Endpunkte per X-Status-Token ist sofort Pflicht.

Out of Scope für Phase 1

  • Automatische Inventarisierung über Zerops API.
  • Automatische Domain-Erkennung aus Zerops.
  • Direkte öffentliche Checks auf Postgres, GeoDB oder Object Storage.
  • Vollständiges Incident-Management mit Eskalationen.

3. Status-Endpunkt-Konvention

Jeder öffentlich erreichbare Service bekommt zwei konsistente Endpunkte:

Endpoint Zweck Dependencies HTTP-Status
GET /_status/live Prozess oder Webserver erreichbar. Keine externen Dependencies. 200, wenn der Service antwortet.
GET /_status/ready Service ist betriebsbereit. Prüft relevante Dependencies, z. B. DB, Backend, Storage oder GeoDB. 200 bei ok, 503 bei degraded/down.
Pflicht: Status-only Endpunkte müssen X-Status-Token validieren. Ohne gültigen Token gibt der Service 404 zurück, damit die Endpunkte nicht als öffentliche API sichtbar werden. Der Token bleibt ausschließlich serverseitig im Poller oder Worker. Bestehende Public-Routen wie Website-Startseiten, API-Smoke-Routen oder API-Dokumentation bleiben öffentliche Reachability-Checks und dürfen durch diese Regel nicht für normale Nutzer gesperrt werden.

4. Service-Antwortformat

Die Services liefern Momentaufnahmen ihres lokalen Zustands. Externe Ping-Zeit und historische Uptime werden von der Status-Website oder einem Poller berechnet. 

{
  "schemaVersion": 1,
  "project": "lmaa.space",
  "service": "backend",
  "environment": "production",
  "status": "ok",
  "checkedAt": "2026-05-26T18:45:00.000Z",
  "startedAt": "2026-05-26T12:00:00.000Z",
  "uptimeSeconds": 24300,
  "version": {
    "gitSha": "optional",
    "buildId": "optional"
  },
  "checks": {
    "database": {
      "status": "ok",
      "latencyMs": 14
    },
    "storage": {
      "status": "ok",
      "latencyMs": 32
    }
  }
}

Statuswerte auf Service-Ebene:

ok - alle relevanten Checks grün
degraded - Teilstörung oder langsame Dependency
down - kritische Dependency oder Service down
unknown - Check fehlt, ist veraltet oder nicht auswertbar

Keine Secrets

Die Antwort enthält keine Connection Strings, internen Hostnames, Tokens, Bucket-Namen, Stacktraces oder rohen Fehlermeldungen. Fehler werden auf stabile Codes gemappt.

6. Ping-Zeiten und Uptime

Vom Poller gemessen

  • responseTimeMs: Zeit von Request-Start bis Response-Ende.
  • httpStatus: tatsächlicher HTTP-Code.
  • tlsValid: optionales TLS-Ergebnis.
  • dnsResolved: optionales DNS-Ergebnis.
  • checkedAt: Zeitpunkt des externen Checks.

Vom Service geliefert

  • uptimeSeconds: Laufzeit des aktuellen Prozesses.
  • startedAt: Startzeit des aktuellen Prozesses.
  • checks.*.latencyMs: interne Dependency-Latenz.
  • checks.*.status: Zustand einzelner Dependencies.

Historisch berechnet

  • Uptime 24h, 7d, 30d und 90d aus Check-Historie.
  • Degraded zählt separat von Down.
  • Timeout, DNS, TLS und 5xx zählen als Down.
  • HTTP 200 mit Service-Status degraded zählt als Degraded.

8. Status-Website UI

Die Status-Website wird als React/Vite-App oder kompatible statische App aufgebaut und nutzt Tailwind CSS, eigene React-Komponenten und semantische CSS Design-Tokens. shadcn/ui wird in der aktuellen Umsetzung bewusst nicht verwendet.

Komponenten

  • Eigene Projekt-, Service-, History-, Incident- und Badge-Komponenten.
  • Projektwechsel über Tabs/Buttons.
  • Servicekarten mit Status, HTTP-Code, Response-Zeit und Uptime.
  • History-Ansicht als kompakte 30-Tage-Balkenmatrix.
  • Lucide Icons für Service-Typen und UI-Aktionen.

Light/Dark Mode

  • Theme-Modi: system, light, dark.
  • Automatisch über prefers-color-scheme.
  • Manuell über eigenen Theme-Toggle.
  • Persistenz über localStorage.
  • Dark Mode orientiert sich an GitHub Dark Dimmed.

Darstellung

  • Kein Hero und keine globale Summary, sondern direkter Einstieg mit Projekten.
  • Projektkarte mit Status und Uptime 24h/7d/30d.
  • Servicekarten ohne öffentlich sichtbare Check-URLs.
  • Cards, Innenflächen, Farben, Radien und Einzüge laufen über Design-Tokens.

9. Polling und Datenaktualisierung

Da Phase 1 ohne Zerops API startet, wird ein Poller mit statischer Config verwendet. Der Poller läuft in der aktuellen Zielarchitektur als GitHub Action.

  1. status.config.json lesen.
  2. X-Status-Token aus STATUS_MONITOR_TOKEN laden und bei Status-only Checks mitsenden.
  3. Alle konfigurierten Check-URLs mit Timeout prüfen.
  4. Response-Zeit, HTTP-Status, JSON-Body und Fehlerklasse erfassen.
  5. Status je Service und Projekt aggregieren.
  6. Historie aktualisieren und Uptime-Fenster berechnen.
  7. status.json und history.json veröffentlichen.

10. GitHub Pages Implementierung

Der Codeberg-/Forgejo-Weg wurde verworfen, weil Forgejo Actions auf Codeberg einen eigenen Runner oder Codeberg-Woodpecker-Onboarding erfordern. Die Status-Website wird stattdessen über GitHub Actions und GitHub Pages veröffentlicht.

GitHub Pages wird auf Source: GitHub Actions konfiguriert. Der Workflow baut die statische App, lädt dist/ als Pages-Artefakt hoch und deployed dieses Artefakt direkt zu GitHub Pages. Ein separater pages-Branch ist nicht nötig.

Empfohlenes Repository-Modell

Für die Status-Seite wird das öffentliche GitHub-Repository phranck/status verwendet.

11. Security

In öffentlichen Statusdaten dürfen keine Secrets, internen Hostnames, Connection Strings, Bucket-Namen, rohen Exceptions oder Stacktraces landen.
  • X-Status-Token ist für Status-only Endpunkte sofort Pflicht.
  • X-Status-Token nur serverseitig im Poller speichern.
  • Ohne Token muss ein Status-only Endpoint 404 liefern, nicht 401.
  • Fehler als stabile Codes ausgeben, z. B. database_unreachable.
  • Public UI zeigt nur aggregierte und sanitisierten Daten.
  • History auf 3 Monate begrenzen. Ältere Detaildaten werden gelöscht oder nur noch aggregiert gehalten.
