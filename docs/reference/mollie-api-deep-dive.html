Mollie ist ein in den Niederlanden (Amsterdam) ansässiger Payment-Service-Provider. Dieses Dokument fasst zusammen, was die Mollie-API leisten kann — mit Fokus auf den für ein Spenden-Feature entscheidenden Punkt: den Bestätigungs-Rückkanal, den der reine GiroCode/EPC-QR-Code nicht liefern kann.

1. Grundlagen & Aufbau

Die Mollie-API ist eine geradlinige REST-API: alle Endpunkte erzeugen, lesen oder aktualisieren Objekte. Sie ist nach Ressourcen gegliedert und gibt JSON zurück.

Base URL https://api.mollie.com/v2/
Version v2 (im URL-Pfad). Aktive, gepflegte Version.
Format JSON. Antworten folgen dem HAL-Stil: Verweise stehen unter _links, eingebettete Listen unter _embedded.
Listen Cursor-basierte Pagination über _links.next / _links.previous.
Beträge Immer als Objekt { "currency": "EUR", "value": "25.00" } — value ist ein String mit fixen Nachkommastellen, nie eine Zahl.
Fehler Standard-HTTP-Codes; Fehlerantworten enthalten status, title, detail und einen Doku-Link.
Offizielle SDKs Mollie pflegt eigene Client-Libraries u.a. für Node.js (@mollie/api-client), PHP, Python. Für ein Hono/Node-Backend wie das von lmaa.space ist der Node-Client die naheliegende Wahl — er kapselt Auth, Pagination und die Webhook-Signaturprüfung.

2. Authentifizierung

Mollie kennt drei Auth-Mechanismen. Alle laufen über den Authorization-Header.

Methode Wofür Eigenschaften
API-Keys Standard-Zahlungsabwicklung im eigenen Account Getrennte Keys mit Präfix test_ und live_, pro Website-Profil. Nur einmal bei Erstellung sichtbar. Mehrere Keys pro Profil möglich (Rotation).
Advanced / Organization Access Tokens Organisationsweite Admin-Ressourcen, mehrere verbundene Accounts Benötigen Admin-Rolle. Nur einmal sichtbar. Unterstützen den testmode-Parameter im Request.
OAuth2 (Mollie Connect) Apps, die im Namen fremder Mollie-Accounts handeln Autorisierungs-Flow mit Nutzer-Consent. App-Access-Tokens. Für Plattform-/Marktplatz-Szenarien.
Für lmaa.space relevant Ein klassischer API-Key (test_ beim Bauen, live_ in Produktion) reicht vollständig. OAuth/Organization-Tokens braucht nur, wer Zahlungen für Dritte abwickelt.

3. API-Ressourcen im Überblick

Ressource Zweck
Payments Kern der API. Einzelzahlungen erzeugen, lesen, aktualisieren, abbrechen.
Methods Verfügbare Zahlungsmethoden abfragen (z.B. um die Auswahl im eigenen Checkout zu rendern).
Payment Links Lang lebende, teilbare Bezahl-Links — ohne eigenen Checkout-Code.
Refunds Voll- und Teilrückerstattungen zu einer Zahlung.
Chargebacks Rückbuchungen lesen (read-only).
Captures Autorisierte Beträge einziehen (bei captureMode: manual).
Customers Kundenobjekte für wiederkehrende Zahlungen.
Mandates Einzugsermächtigungen — Basis für Recurring.
Subscriptions Automatisch wiederkehrende Zahlungen in festen Intervallen.
Orders deprecated Bestell-Objekte mit Positionen. Nicht mehr empfohlen — siehe Kasten unten.
Settlements Auszahlungs-Sammelposten — welche Transaktionen in welcher Auszahlung steckten.
Balances Kontostände und Buchungen je Währung.
Payouts Auszahlungen auf das eigene Bankkonto.
Invoices Mollies Rechnungen an dich (Gebührenabrechnung).
Profiles Website-Profile (pro Profil eigener API-Key, eigene vIBAN).
Organizations Organisations-Stammdaten.
Terminals Point-of-Sale-Terminals (physische Kartenzahlung).
Webhooks & Webhook Events Next-Gen-Webhooks: dauerhafte Event-Abos + Event-Historie. Siehe Abschnitt 5.
Orders API ist deprecated Mollie empfiehlt die Orders API nicht mehr und verweist auf die Payments API. Die Payments API unterstützt inzwischen lines (Positionen), allerdings unveränderlich nach dem Anlegen. Einzige Ausnahme: Pay-after-delivery-Methoden (Klarna „Pay later", Billie, Riverty) brauchen weiterhin die Orders API. Für ein Spenden-Feature ist das irrelevant — dort wird ausschließlich die Payments API gebraucht.

4. Payments API

Die Payments API ist das Herz von Mollie. Der Grundablauf hat drei Schritte:

  1. Zahlung per POST /v2/payments erzeugen.
  2. Kunden auf die zurückgegebene _links.checkout-URL leiten (Mollie-Hosted-Checkout).
  3. Bei Statuswechsel ruft Mollie deinen Webhook — du holst den finalen Status per API.

Zahlungs-Status

Status Bedeutung
open Erstellt, Kunde hat noch nicht bezahlt.
pending Zahlung läuft, Ergebnis noch offen — z.B. eine SEPA-Überweisung, die unterwegs ist.
authorized Betrag autorisiert, aber noch nicht eingezogen (bei captureMode: manual).
paid Erfolgreich bezahlt — Geld ist eingegangen. Der Zielzustand.
canceled Vom Kunden oder von dir abgebrochen.
expired Session abgelaufen, ohne dass bezahlt wurde.
failed Zahlung fehlgeschlagen.

Wichtige Parameter bei POST /v2/payments

Feld Beschreibung
amount pflicht Objekt aus currency + value (String).
description pflicht Erscheint auf dem Kontoauszug des Kunden, max. 255 Zeichen.
redirectUrl Wohin der Kunde nach dem Bezahlvorgang zurückkehrt.
cancelUrl Eigene Rücksprung-URL, wenn der Kunde aktiv abbricht.
webhookUrl Der Rückkanal. Öffentlich erreichbare URL, die Mollie bei jedem Statuswechsel aufruft.
method Eine Methode oder ein Array — z.B. banktransfer, ideal, creditcard, paypal, bancontact, applepay. Über 35 Methoden verfügbar.
metadata Beliebige eigene Daten (String oder JSON) — Mollie speichert sie am Objekt. Ideal für eine eigene Spenden-ID.
locale Sprache der Hosted-Checkout-Seite, z.B. de_DE.
sequenceType oneoff · first · recurring — steuert Einmal- vs. wiederkehrende Zahlung.
customerId / mandateId Verknüpfung für wiederkehrende Zahlungen.
captureMode / captureDelay automatic (Standard) oder manual; optionaler Einzug-Verzug (max. 7 Tage).
dueDate Fälligkeitsdatum (YYYY-MM-DD) — relevant für Überweisungen.
lines, billingAddress, shippingAddress Positionen/Adressen; für manche Methoden Pflicht, für eine Spende nicht nötig.

Beispiel — Spende anlegen

# Einmalige 25-EUR-Spende per SEPA-Überweisung
curl -X POST https://api.mollie.com/v2/payments \
  -H "Authorization: Bearer test_xxxxxxxxxxxxxxxxxxxx" \
  -H "Idempotency-Key: 6f7a1c4e-..." \
  -d "amount[currency]=EUR" \
  -d "amount[value]=25.00" \
  -d "description=Spende lmaa.space" \
  -d "method=banktransfer" \
  -d "redirectUrl=https://lmaa.space/spende/danke" \
  -d "webhookUrl=https://api.lmaa.space/webhooks/mollie" \
  -d "metadata[donationId]=dn_2026_0042"

5. Webhooks — der Rückkanal

Genau das, was der GiroCode nicht kann: Mollie meldet aktiv zurück, wenn sich der Zahlungsstatus ändert. Es gibt zwei Generationen, die parallel existieren.

5.1 Klassische Webhooks (pro Ressource)

Diese sind das primäre Mittel, um über eine einzelne Zahlung informiert zu werden — also der direkte Weg für die Spenden-Bestätigung.

Registrierung Über den webhookUrl-Parameter beim Anlegen der Zahlung (bzw. Subscription / Payment Link).
Payload Minimaler POST — nur die ID, z.B. id=tr_5B8cwPMGnU6qLbRvo7qEZo. Der Status wird bewusst NICHT mitgeschickt.
Antwort Dein Endpunkt muss 200 OK zurückgeben. Jeder andere Code löst einen Retry aus.
Statusabruf Du musst mit der ID die API zurückrufen (GET /v2/payments/{id}) und den echten Status holen.
Retries Bis zu 10 Versuche über 26 Stunden, exponentielles Backoff (1, 2, 4, … Minuten). Timeout je Aufruf: 15 Sekunden.
Unterstützt von Payments, Orders, Subscriptions (je generierte Zahlung), Payment Links.
Warum der Payload „dumm" ist — und warum das gut ist Weil der Webhook keinen Status transportiert, kann ein gefälschter Webhook-Aufruf nichts auslösen: Er enthält ja keine vertrauenswürdige Information. Du fragst immer bei Mollie nach. Damit braucht der klassische Webhook keine Signaturprüfung — Sicherheit entsteht durch den authentifizierten API-Rückruf.

5.2 Next-Gen-Webhooks (account-weite Events)

Die neuere Generation: dauerhafte Abonnements auf bestimmte Event-Typen der ganzen Organisation, statt einer URL pro einzelner Ressource.

Mechanik Du abonnierst Event-Typen einmalig. Mollie schickt strukturierte Event-Objekte per POST.
Payload-Wahl Entweder voller Snapshot mit kompletten Ressourcendaten oder minimal (nur IDs + Event-Typ).
Signatur HMAC-SHA256 im Header X-Mollie-Signature: sha256=… — verifizierbar mit einem Signing-Secret. Hier ist Signaturprüfung Pflicht.
Event-Typen U.a. payment-link.paid, payout.*, sales-invoice.*, balance-transaction.created, business-account-transfer.*, oder * für alle.
Zusatz-APIs Webhooks API (Abos verwalten) und Webhook Events API (Event-Historie nachladen / Echtheit prüfen).
Limits Testmodus: 1 aktives Abo. Live: bis zu 3 Abos. Empfehlung: eine URL für alle relevanten Event-Typen.
Secret-Rotation Im Dashboard „Roll secret" — das alte Secret läuft innerhalb eines Tages ab.
Wichtige Unterscheidung für die Spenden-Bestätigung Die Next-Gen-Events decken aktuell vor allem account-weite Vorgänge ab (Payment Links, Payouts, Rechnungen, Kontobuchungen). Für die Bestätigung einer konkreten Einzelzahlung bleibt der klassische webhookUrl am Payment der direkte Weg. Wenn ihr mit der Payment Links API arbeitet, ist payment-link.paid als signiertes Next-Gen-Event hingegen sehr attraktiv.

5.3 Webhook-Handler — Skizze (Hono/Node)

app.post('/webhooks/mollie', async (c) => {
  // 1. Payload enthält nur die ID — niemals dem Payload trauen.
  const { id } = await c.req.parseBody();

  // 2. Echten Status frisch von Mollie holen (authentifiziert).
  const payment = await mollieClient.payments.get(id);

  // 3. Idempotent verbuchen: Webhook kann mehrfach feuern.
  if (payment.status === 'paid') {
    await recordDonationOnce(payment.id, payment.amount, payment.metadata);
  }

  // 4. Schnell mit 200 antworten (Timeout 15 s).
  return c.body(null, 200);
});

6. Payment Links API

Payment Links sind lang lebende, teilbare Bezahl-Links — im Gegensatz zu den kurzlebigen Checkout-URLs der Payments API. Ideal, wenn der Spender „irgendwann" zahlen soll, oder wenn man möglichst wenig eigenen Checkout-Code schreiben will.

Aspekt Detail
Felder amount (optional — ohne Betrag gibt der Zahler ihn selbst ein), description, redirectUrl, webhookUrl, expiresAt, reusable.
reusable Erlaubt, denselben Link für mehrere Zahlungen zu verwenden — perfekt für einen dauerhaften „Jetzt spenden"-Link.
Endpunkte Create, Get, List, Update, Delete sowie „List payment link payments" (die einzelnen Zahlungen zu einem Link).
Rückkanal Eigener webhookUrl am Link plus das Next-Gen-Event payment-link.paid.
Spannend für ein Spenden-Feature Ein reusable Payment Link ohne festen Betrag ist faktisch eine fertige, gehostete Spendenseite — mit Betragseingabe durch den Spender und Bestätigung per Webhook, ganz ohne eigenen Checkout.

7. SEPA im Detail

Mollie bietet zwei SEPA-Wege. Sie unterscheiden sich grundlegend — vor allem beim Rückbuchungsrisiko, was für anonyme Spenden entscheidend ist.

  SEPA-Überweisung banktransfer SEPA-Lastschrift directdebit
Prinzip Kunde überweist selbst aus seiner Banking-App (Push). Mollie zieht den Betrag vom Konto ein (Pull).
Rückbuchungsrisiko keines Kein Chargeback-Risiko. hoch Widerruf 8 Wochen ohne Begründung; bei „unautorisiert" bis 13 Monate.
Recurring Nein. Ja — Standard für wiederkehrende Euro-Zahlungen, auch monatliche Spenden.
Währung / Betrag nur EUR · 0,01 – 1.000.000,00 nur EUR · 0,01 – 1.000,00 (Standardlimit)
Session 12 (+2) Tage — Zeit, in der der Kunde überweisen kann. 60 bzw. 15 Minuten.
Settlement 2 Werktage 9 Werktage
Refund-Fenster 365 Tage (voll & teilweise) 365 Tage (voll & teilweise)
Mandat nötig Nein. Ja — siehe Abschnitt 8.

Wie die Überweisung abläuft

  • Mollie zeigt dem Kunden die Zahldaten direkt am Bildschirm oder per E-Mail — inklusive QR-Code, der die Bankdaten in der Banking-App vorausfüllt.
  • Lokalisierte virtuelle IBAN (vIBAN): Mollie hat eigene Bankkonten für DE, NL, BE, FR. Ein deutscher Spender überweist also auf eine deutsche IBAN — das senkt Abbruchraten deutlich. Die vIBAN wird pro Website-Profil erzeugt.
  • Auf dem Kontoauszug des Spenders erscheint der Trade-Name des Profils + „via Mollie".
  • Statusverlauf: open → (Geld unterwegs) → paid, sobald der Eingang erkannt wird. Genau dann feuert der Webhook.
  • Standard-SEPA dauert 1–2 Werktage; SEPA Instant settled in ~10 Sekunden, 24/7 — mit Echtzeit-Webhook.

Verfügbar für Zahler aus EU/EEA, UK und der Schweiz; Händler-Sitz: EEA, UK, Schweiz.

8. Recurring: Customers, Mandates, Subscriptions

Wiederkehrende Zahlungen (z.B. monatliche Dauerspenden) bauen auf drei Objekten auf:

Customer

Ein Kundenobjekt, an dem Mandate und Zahlungen hängen.

Mandate

Die Einzugsermächtigung — „der Kunde erlaubt dir, sein Konto/seine Karte wiederholt zu belasten". Entsteht automatisch bei der ersten Zahlung (sequenceType: first) oder direkt über die Mandates API.

Subscription: plant automatische Zahlungen in festen Intervallen (interval, times, startDate). Jede generierte Zahlung ruft den hinterlegten Webhook. Hinweis: Die Subscriptions API ist nicht zwingend — wiederkehrende Zahlungen lassen sich auch selbst über die Payments API mit gespeichertem Mandat steuern.

Erstzahlung erklärt das Mandat Bei der ersten Lastschrift-Zahlung sieht der Kunde Infos über deine Organisation und bestätigt mit dem Konto, das künftig belastet wird. Folgezahlungen laufen dann ohne erneute Interaktion über das Mandat (sequenceType: recurring).

9. Refunds, Chargebacks, Captures

API Was sie tut
Refunds Voll- oder Teilrückerstattung einer Zahlung über einen Betrag. Mehrere Teil-Refunds möglich. Refund-Fenster bei SEPA: 365 Tage.
Chargebacks Read-only: Rückbuchungen einsehen (vor allem bei Karte und Lastschrift relevant).
Captures Bei captureMode: manual autorisierte Beträge einziehen. Capture erfolgt betragsbasiert, nur für Zahlungen im Status authorized.

10. Settlements, Balances, Payouts & Invoices

API Zweck
Balances Kontostände je Währung + Buchungsliste + Balance-Report. Zeitbasierte Buchhaltung.
Settlements Auszahlungs-Sammelposten: welche Zahlungen, Refunds, Chargebacks in welcher Auszahlung enthalten waren. Inklusive „open" und „next" settlement.
Payouts Auszahlungen aufs eigene Bankkonto anstoßen/lesen/abbrechen.
Invoices Mollies Gebührenrechnungen an dich.

11. Idempotenz

Header Idempotency-Key — wird bei allen POST-Endpunkten akzeptiert.
Verhalten Gleicher Key innerhalb einer Stunde → Mollie liefert die gecachte Erstantwort statt neu zu verarbeiten.
Erkennung Replay erkennbar am Antwort-Header Idempotent-Replayed: true.
Ablauf Keys älter als 1 Stunde fallen aus dem Cache — danach gilt der Key als neue Anfrage.
Fehler 400 bei abweichendem Request zum selben Key; 409 bei gleichzeitigen Requests mit identischem Key.
Empfehlung UUID4 als Key. Besonders wichtig bei Recurring, Subscriptions und Teil-Refunds — dort führt ein blinder Retry sonst zu Doppelbelastungen.

12. Testing

  • Testmodus über einen test_-API-Key oder den testmode-Parameter (bei Org-/App-Tokens). Testdaten sind vollständig von Live-Daten isoliert.
  • Testzahlungen haben eine eigene Test-Checkout-Seite — der Bezahlvorgang lässt sich ohne echtes Geld durchlaufen.
  • „Magic Amounts" erzwingen Fehlerszenarien bei Karten: z.B. 1001.00 = ungültige Kartennummer, 1004.00 = Karte abgelaufen, 1007.00 = unzureichende Deckung.
  • Testkartennummern für Visa/Mastercard/Amex (beliebiges Ablaufdatum/CVV).
  • Wiederkehrende Testzahlungen liefern eine changePaymentState-URL zum manuellen Umschalten des Status.
Webhooks lokal testen Mollie kann localhost nicht erreichen. Für lokale Webhook-Tests braucht es einen Tunnel (z.B. cloudflared) mit öffentlicher HTTPS-URL. Auf Zerops ist der Backend-Endpunkt ohnehin öffentlich erreichbar.

13. Aktuelle Entwicklungen 2025/2026

  • Alle 35+ Zahlungsmethoden auf der Payments API (April 2025) — auch Klarna, Billie, Riverty laufen jetzt über die Payments API.
  • Orders API deprecated — Migration auf die Payments API empfohlen; lines dort unveränderlich.
  • Next-Gen-Webhooks mit signierten Events (HMAC-SHA256), Event-Abos und Event-Historie.
  • Karten im Checkout speichern über die Payments API — eingebettete 1-Click-Zahlung ohne Redirect.
  • Mollie Outbound Payments — API-first-Lösung für ausgehende Instant-SEPA-Überweisungen (Auszahlungen an eigene Nutzer).
  • Google Pay über alle drei Interfaces (Checkout, Components, API); Multiple Currency Balances; Terminal Pairing Codes per API; Mollie Insights-Dashboard.
  • Vereinheitlichung der API-Identifier — Mollie standardisiert seine Ressourcen-IDs (Payment- und Order-IDs betroffen).

14. Einordnung für lmaa.space & musiccloud

Für das geplante Spenden-Feature lassen sich die Bausteine konkret zuordnen:

Baustein Empfehlung
API Payments API. Die Orders API wird nicht gebraucht.
Methode banktransfer als Default für anonyme Einzelspenden — kein Rückbuchungsrisiko. Karte/iDEAL/PayPal optional zusätzlich. Lastschrift nur bewusst für Dauerspenden.
Rückkanal Klassischer webhookUrl am Payment. Handler holt Status per GET, verbucht paid idempotent.
Alternative ohne Checkout-Code Ein reusable Payment Link ohne festen Betrag = fertige gehostete Spendenseite, Bestätigung via payment-link.paid.
Auth Ein API-Key je Umgebung (test_ / live_).
Robustheit Idempotency-Key beim Anlegen; Webhook-Handler idempotent (Status prüfen, bevor verbucht wird).
Betrieb Webhook-Endpunkt öffentlich + HTTPS (Zerops-Backend passt). Lokal: Tunnel. Eigene Spenden-ID in metadata ablegen.
Cross-Projekt „Payment anlegen + Webhook verarbeiten" ist in lmaa.space und musiccloud dieselbe Form. Ein gemeinsames Package lohnt nur, falls beide im selben Monorepo liegen — sonst pro Projekt dünn nachbauen.

Der GiroCode/EPC-QR-Code bleibt sinnvoll als provider- und gebührenfreier Default. Mollie ergänzt genau das fehlende Stück: die automatische Bestätigung, dass eine Spende angekommen ist.
